# 农场管家系统 开发宪法

## Core Principles

### I. 数据准确性 (Data Accuracy)

所有传感器采集数据、传输链路和处理逻辑 MUST 确保数据的准确性。

- 传感器采集层 MUST 实施数据校验机制，包括量程校验、变化率校验和时序校验。
- 数据传输链路 MUST 采用校验和（如 CRC、MD5）或数字签名确保数据完整性，防止传输篡改或损坏。
- 数据处理管道 MUST 在入库前对每一批次数据进行完整性核对，计量精度误差不超过 ±0.5%。
- 数据库存储层 MUST 使用强类型字段约束，禁止模糊数据类型（如全用 `VARCHAR` 存储数值）。
- 任何数据校验失败 MUST 产生告警并记录详细日志，不得静默跳过。
- 校准与标定流程 MUST 定期执行，相关操作 MUST 留存操作记录。

**理由**: 农业场景中，温度、湿度、土壤墒情、光照等数据的细微偏差可能导致错误的灌溉决策、施肥方案或病害预警，直接影响作物产量与品质。

### II. 操作流程可追溯 (Operation Traceability)

系统中所有关键操作 MUST 具备完整的审计追溯能力。

- 每一次数据写入、配置变更、设备控制指令 MUST 记录操作者、操作时间、操作内容、操作前后状态。
- 审计日志 MUST 写入不可篡改的持久化存储，保留期限不少于 1 年。
- 追溯记录（质量追溯数据）MUST 永久保存，不可删除、不可篡改，适用独立于审计日志的保留策略。
- 日志 MUST 包含以下维度的可追溯信息：谁（操作者 ID/IP）、何时（精确到毫秒的时间戳）、做了什么（操作类型与参数）、结果（成功/失败/异常）。
- 设备控制指令（如水泵开关、通风控制）MUST 记录完整的命令链路：下发→执行→结果回执。
- 审计日志的查询 API MUST 支持按时间范围、操作者、操作类型等多维度筛选。

**理由**: 农业物联网涉及物理设备的远程控制与生产资料管理，操作不可追溯将导致事故无法定位、责任无法界定，且不符合监管合规要求。

### III. 权限与访问控制 (Role-Based Access Control)

系统的每一个操作入口 MUST 基于明确的权限模型进行访问控制。

- 采用 RBAC（基于角色的访问控制）模型，至少定义以下角色层级：系统管理员、农艺师、操作员、只读观察者。
- 每个 API 端点（前端页面）MUST 声明所需的权限级别，未授权访问 MUST 返回 403。
- 细粒度权限控制：同角色用户对不同区域/大棚/地块的数据访问范围 SHOULD 可按需限制。
- 认证机制 MUST 采用 JWT 或 OAuth2，Token 有效期不超过 2 小时，支持 Refresh Token 续期。
- 密码策略 MUST 强制最小长度 8 位，包含字母与数字组合，连续失败 5 次后锁定账户 15 分钟。
- 权限变更操作（角色分配、权限提升）MUST 由更高权限者审批并留存审计记录。

**理由**: 农业数据涉及经营决策，设备控制涉及生产安全，不合规的访问可能导致财产损失或安全事故。

### IV. 易用性 (Usability)

系统界面和交互流程 MUST 以目标用户（农业从业者）的认知水平和操作习惯为设计出发点。

- 核心操作（查看实时数据、开启/关闭设备、查看告警）MUST 在不超过 3 次点击/触达内完成。
- 数据展示 MUST 以可视化图表（折线图、仪表盘、热力图）为主，原始表格为辅。
- 错误提示 MUST 使用用户可理解的自然语言，不得直接暴露系统异常堆栈。
- 系统 MUST 支持移动端响应式布局，在 320px 宽度设备上核心功能可正常使用。
- 关键告警 SHOULD 支持短信/微信公众号/APP 推送等即时通知渠道；v1 默认仅提供系统内消息通知，预留外部推送接口。
- 界面语言默认中文，关键术语（如传感器名称、设备类型）MAY 在初始化时提供自定义配置。

**理由**: 农业物联网的最终用户通常是农场工人和农技人员，而非 IT 专业人员，高学习成本将导致系统弃用。

### V. 实时监控与异常数据拒绝 (Real-time Monitoring & Abnormal Data Gate)

系统 SHOULD 对传感数据流进行实时监控，并在入库前拦截异常数据。当 IoT 传感器接入时，MUST 启用实时监控与异常数据拒绝机制。

- 数据采集频率 SHOULD 可配置（默认每 30 秒一次），监控面板刷新延迟不得超过 3 秒。
- 异常数据判定规则 MUST 支持：物理量程越界、时间戳乱序、空值/零值异常、单点突变（与前后值偏差超过 3σ）、长期无变化（死值检测）。
- 被判定为异常的数据 MUST 被拦截并写入"异常数据隔离表"，不得进入正常业务数据集参与计算。
- 异常数据拦截事件 MUST 触发实时告警，并在监控面板高亮标记异常设备。
- 数据恢复策略：确认传感器故障修复后，MAY 通过人工审核将隔离数据回补，但 MUST 附加人工审核标记。
- 设备离线检测：单设备超过可配置阈值（默认 5 分钟）无数据上报时，SHOULD 触发离线告警。

**理由**: "垃圾进，垃圾出"——异常数据若进入业务决策链，将导致灌溉过量/不足、施肥错误等连锁灾害，隔离异常数据是系统可靠性的最后防线。

## 技术约束与安全要求

### 技术栈约束

- 后端服务 MUST 支持 Linux 环境部署，推荐语言为 Node.js（TypeScript）或 Python ≥ 3.11。
- 数据库 MUST 使用时序数据库（如 InfluxDB、TimescaleDB、TDengine）作为传感数据主存储，MySQL 作为业务数据与审计日志存储。
- 前端框架 MUST 支持组件化开发，推荐 Vue 3 + TypeScript 或 React 18 + TypeScript。
- 设备通信协议默认采用 MQTT（QoS ≥ 1），MUST 支持 TLS 加密传输。

### 安全要求

- 所有网络通信（API、MQTT）MUST 启用 TLS 1.2+ 加密。
- 设备凭证 MUST 支持一机一密，不得使用共享密钥。
- SQL/NoSQL 查询 MUST 使用参数化查询，禁止字符串拼接。
- 敏感配置（数据库密码、密钥）MUST 通过环境变量或配置中心注入，不得硬编码或提交版本控制。

### 性能要求

- 传感数据写入吞吐量 MUST 支持不少于 500 点/秒。
- 监控面板 API 响应时间 P95 ≤ 200ms。
- 单设备数据点查询（24 小时范围）P95 ≤ 500ms。

## 开发流程与质量门禁

### 分支策略

- 采用 Git Flow 或 Trunk-Based Development 分支模型。
- 主分支（`main`/`master`）MUST 受保护，禁止直接推送。
- 功能开发 MUST 在特性分支上进行，通过 Pull Request 合并。

### 代码审查

- 所有合并至主分支的 PR MUST 经过至少 1 名其他开发者审查。
- 审查 MUST 关注：功能正确性、异常处理完善性、安全漏洞、与宪章原则的符合性。

### 测试要求

- 核心数据校验逻辑 MUST 有单元测试覆盖，覆盖率 ≥ 80%。
- API 端点 MUST 有集成测试覆盖。
- 异常数据拒绝逻辑 MUST 有专项测试用例（包含各类异常数据类型）。

### 文档要求

- API 接口 MUST 使用 OpenAPI 3.0 规范生成文档。
- 数据库表结构变更 MUST 配套迁移脚本和变更说明。
- 设备接入协议 MUST 编写对接文档，包含主题定义、数据格式、错误码映射。

## Governance

本宪法是项目的最高治理文件，所有设计决策、代码实现和运维操作 MUST 与其保持一致。

### 修订程序

1. 任何团队成员可提出修订提案，描述变更内容、理由及影响范围。
2. 提案 MUST 经过团队评审，至少获得 70% 核心成员同意方可生效。
3. 修订生效后 MUST 同步更新依赖模板（plan、spec、tasks）中的相关检查项。
4. 修订须在宪法文件中记录版本变更日志。

### 版本管理

- 版本号遵循语义化版本规范：MAJOR.MINOR.PATCH。
- MAJOR：新增/移除原则，或对已有原则进行不兼容的重大重定义。
- MINOR：新增章节或对已有内容进行实质性扩展。
- PATCH：措辞修正、排版优化、非语义性调整。

### 合规审查

- 每个 PR/Code Review MUST 验证变更是否违反任何宪法原则。
- 实施计划（plan.md）中的"宪法检查"Gate MUST 逐条对照原则通过后方可进入实现阶段。
- 每季度进行一次宪法合规回顾，评估现有原则的有效性和适用性。
